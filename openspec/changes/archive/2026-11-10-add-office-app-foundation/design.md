# Design

## Context

See `proposal.md` for motivation. The repository contains only an OpenSpec configuration and a one-line README, so this design establishes the application stack, routing, data model, and storage boundary from scratch. The constraints that shape it are: schools may run the app on a single inexpensive server or a shared managed database; the same build must work with SQLite and PostgreSQL; and this release ships read-only editor shells, so the data model must not lock in a document-content format yet.

## Goals / Non-Goals

**Goals:**

- One deployable process that serves the UI and the document API.
- A storage boundary that later editor changes can extend with content tables without changing the file-library behavior.
- Identical validation and error outcomes on both database backends.
- A tab layout that remains understandable without client-side state on first load.

**Non-Goals:**

- A plugin system for editors, real-time collaboration, or offline editing.
- Defining document content schemas for Word, Excel, PowerPoint, or Drawing.
- Multi-tenant isolation or per-user ownership (deferred to `add-school-accounts`).
- Supporting database backends beyond SQLite and PostgreSQL.

## Decisions

### Stack: Next.js App Router with TypeScript

Use Next.js (App Router) with React and TypeScript as a single full-stack process. Server Components load the dashboard and document metadata; small client components handle tabs, dialogs, and optimistic UI. Route handlers under `/api` provide the document operations and health endpoint.

*Alternatives considered:* a separate React SPA plus Express API adds a second deployable and CORS configuration for no benefit at this size; a server-rendered framework without a client router would make the persistent tab shell harder to implement.

### Styling: CSS Modules with shared design tokens

Use CSS Modules and a small set of CSS custom properties for color, spacing, and typography. This keeps the build minimal and avoids a utility-framework dependency. The shell is responsive from 360px upward; tabs scroll horizontally rather than collapse into a menu.

*Alternatives considered:* Tailwind CSS is faster to prototype but adds build configuration and markup noise; a component library is unnecessary for five screens.

### Data access: explicit repository over two thin drivers

Define a `DocumentRepository` interface (list, get, create, rename, delete) in a shared server module. Implement it with `better-sqlite3` and `pg`, using parameterized SQL and one migration set per dialect. A migration runner applies numbered SQL files in a transaction and records applied versions in `schema_migrations`.

*Alternatives considered:* Prisma hides dialect differences but adds a generation step, a large runtime, and provider-specific migration folders; Drizzle still requires separate SQLite and PostgreSQL schema definitions and migrations; Kysely is a good query builder but does not remove the need for per-dialect migrations, so for one table the extra abstraction is not justified. The repository interface is the seam that keeps the rest of the app unaware of the backend.

### Configuration: environment variables validated at startup

Configuration is parsed once by a Zod schema:

- `DATABASE_BACKEND` — `sqlite` (default) or `postgres`.
- `DATABASE_URL` — PostgreSQL connection string; when present and no backend is set, selects `postgres`.
- `DATABASE_PATH` — SQLite file path, default `./data/soffice.db`.
- `PORT` — HTTP port, default `3000`.

Invalid or contradictory settings stop startup with a message naming the variable. Error messages and health responses never include the connection string or password. The data directory is created if missing, and the SQLite file lives on a persistent volume in deployment.

### Data model: backend-neutral identifiers and normalized names

The `documents` table stores:

| Column | SQLite | PostgreSQL | Notes |
| --- | --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | `uuid PRIMARY KEY` | UUID generated by the application, so both backends receive the same value |
| `name` | `TEXT NOT NULL` | `text NOT NULL` | Display name, trimmed, 1–120 characters |
| `name_key` | `TEXT NOT NULL UNIQUE` | `text NOT NULL UNIQUE` | `NFKC`-normalized, trimmed, lower-cased name used for case-insensitive uniqueness |
| `type` | `TEXT NOT NULL CHECK (...)` | `text NOT NULL CHECK (...)` | One of `word`, `excel`, `powerpoint`, `drawing` |
| `created_at` | `TEXT NOT NULL` | `timestamptz NOT NULL` | UTC; serialized as ISO 8601 from the repository |
| `updated_at` | `TEXT NOT NULL` | `timestamptz NOT NULL` | Updated by the repository on rename and creation |

Names are normalized in application code before every write so uniqueness does not depend on database collation. Unique-constraint violations are translated into a domain `NameConflict` error (SQLite constraint code, PostgreSQL `23505`). This deliberately has no content column; editor changes will add type-specific content tables keyed by document id.

### Routing: type-scoped workspace paths

- `/` — dashboard and file library.
- `/word`, `/excel`, `/powerpoint`, `/drawing` — workspace empty state for that type.
- `/word/[id]` (and equivalents) — document shell.
- `/api/documents`, `/api/documents/[id]`, `/api/health` — JSON operations.

A request for `/word/[id]` where the document is not a Word document responds with a redirect to the correct type path, satisfying the address-mismatch scenario. NotFound responses render a not-found state with a Library link.

Tabs are links to the last active document of each type. The last active id per type is kept in `sessionStorage`; the workspace root route resolves it on the client and replaces the address with the document path when the document still exists. This restores the previous document when switching tabs, without putting per-user state on the server.

### Migrations and startup

Migrations run from Next.js's `instrumentation.ts` startup hook before the server accepts traffic. The migration runner:

1. Opens the configured connection.
2. Creates `schema_migrations` if absent.
3. Applies each pending migration in a transaction.
4. Fails startup on any error.

For PostgreSQL, a session-level advisory lock (`pg_advisory_lock`) around the runner prevents two instances from migrating concurrently. SQLite deployments are single-process by design; the run is still transactional and re-runnable.

### Health endpoint

`GET /api/health` returns `{ status, storage: { status, backend } }` and uses HTTP 200 when the database answers `SELECT 1`, otherwise HTTP 503 with a fixed, non-sensitive reason. The backend name (`sqlite` or `postgres`) is reported; credentials and paths are not.

### Testing

- Unit tests for name normalization, validation, and error translation.
- A shared repository contract suite parameterized over SQLite (temporary file) and PostgreSQL (docker-compose service), covering ordering, uniqueness, timestamps, and restart persistence.
- Component tests for tab navigation and empty/error states.
- End-to-end tests with Playwright for create, rename, delete, open, reload, and read-only shell behavior.

## Risks / Trade-offs

- **Native SQLite dependency fails to build on some hosts** → prefer prebuilt binaries, run the production image on a Debian-based container, and document build prerequisites in the README.
- **The two SQL dialects drift** → the shared contract suite runs against both backends; any schema change must add both migration files and pass both runs.
- **Case-insensitive uniqueness differs by locale** → normalize names in application code with a fixed locale-independent rule and store the result in `name_key`, rather than relying on database collation.
- **Next.js startup hook runs migrations more than once** → migrations are written to be idempotent and PostgreSQL uses an advisory lock; SQLite is documented as single-instance.
- **Read-only shells may disappoint users expecting editing** → every shell carries an explicit notice and the README lists the upcoming editor changes.
- **Session-based tab restoration is per browser tab** → acceptable for a simple app; the document remains reachable from the dashboard and via its address.

## Migration Plan

Greenfield release; there is no existing data to migrate.

1. Add the application skeleton, configuration, and migration runner.
2. Ship the document schema and repository with both migrations.
3. Deploy with the default SQLite volume for a single school server, or set `DATABASE_URL` for PostgreSQL.
4. Rollback is a redeploy of the previous version; because no content exists yet, dropping the `documents` table is safe if a full reset is required.

## Open Questions

None. Authentication, sharing, and document content formats are explicitly deferred to follow-up changes listed in the proposal.
